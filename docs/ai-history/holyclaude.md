# HolyClaude history

History moved verbatim from `kubernetes/apps/ai/CLAUDE.md` on 2026-09-25 (#710); current state lives in that file.

## Omniroute-routed Claude Code auth reverted (2026-09-26)

The 2026-09-16 to 2026-09-26 Omniroute-backed Claude Code auth mechanism
described in full below (`OMNIROUTE_ANTHROPIC_BASE_URL`/
`OMNIROUTE_ANTHROPIC_MODEL` env vars, the `postStart` hook that patched
`~/.claude/settings.json`, the `holyclaude-interactive` Omniroute key on the
`coding-deep` combo) was reverted at the operator's request. It never
provided real fallback resilience despite its multi-leg combo shape (see
the "CORRECTED 2026-09-17" finding in the section below and the full
writeup in `docs/superpowers/specs/2026-09-16-omniroute-anthropic-lane-design.md`'s
"Outcomes / findings") and made HolyClaude's interactive session fail
closed on any Omniroute hiccup, rather than degrading gracefully as its
naming implied. Claude Code is back to the original native `claude login`
OAuth device-flow session (`persist-claude-json.mjs`, per the 2026-09-01
design below), persisted on HolyClaude's own PVC, talking directly to
Anthropic with no `ANTHROPIC_BASE_URL`/API-key override. TaskMaster AI,
OpenCode, Hindsight, `kube-mcp`, and every other HolyClaude provider/plugin
were unaffected — this change is scoped to the Claude Code provider only,
mirroring the original 2026-09-16 switchover's own stated scope in reverse.
See `docs/superpowers/plans/2026-09-26-holyclaude-omniroute-revert.md` for
the implementation notes and `kubernetes/apps/ai/CLAUDE.md`'s holyclaude
bullet for current state.

## HolyClaude deployment notes (2026-09-02 to 2026-09-23)

- **holyclaude** (`kubernetes/apps/ai/holyclaude/`) — [CoderLuii/HolyClaude](https://github.com/CoderLuii/HolyClaude), `holyclaude.68cc.io` (Authentik forwardAuth, `traefik-external-gateway`). A deliberate interactive, human-driven dev workstation authenticated against the user's own Claude Max/Pro subscription — the opposite shape from **openclaw**'s autonomous, local-only-inference role; see the scoped-exception note below for the policy carve-out this creates. Image `docker.io/coderluii/holyclaude` (no GHCR mirror exists — only workload in the cluster pulling from `docker.io`), `full` variant pinned to `1.5.7` (mandatory for OpenCode, which the `slim` build compiles out entirely — choosing `full` also unavoidably bakes in Junie and Pi Coding Agent). Three providers enabled with real credentials: **Claude Code** (Omniroute-backed auth as of 2026-09-16, replacing the earlier native `claude login` OAuth device-flow session entirely for Claude Code specifically — other providers persisted on this PVC, if any, are unaffected: `ANTHROPIC_BASE_URL` is `http://omniroute.ai.svc.cluster.local:20128` — a plain container env value, no secret needed, same cluster-internal pattern every other Omniroute consumer uses — and `ANTHROPIC_AUTH_TOKEN` carries `OMNIROUTE_API_KEY` (SOPS-encrypted in `secret.sops.yaml`), a dedicated Omniroute inference key named `holyclaude-interactive` and scoped via `modelAccessMode: "restricted"` + `allowedCombos: ["coding-fast","coding-deep","debugging","advanced"]` so it can reach only those four routing combos, not the full model/combo catalog. `ANTHROPIC_MODEL` defaults to the `coding-deep` combo — three legs, `cliproxyapi/claude-sonnet-5` → `cliproxyapi/gpt-5.5` → local `llamaswap/coder-large`, not a bare Claude model reference. **This is not a functioning fallback chain, despite the naming** — confirmed by this project's own testing: the middle leg, `gpt-5.5`, is one of the four `cliproxyapi/gpt-*` candidates Task 3 found rejects every request with the same Responses-API-shape-mismatch error as `gpt-5.6-luna` (via real calls with two different auth keys — see "Known Omniroute limitations" below), so it can never actually serve a request; the terminal leg, `llamaswap/coder-large`, resolves to `gpt-oss-20b` (32k slot, since 2026-09-24 #701 — previously `agentic-coder` at `--ctx-size 32768`) (`kubernetes/apps/ai/llama-swap/app/configmap.yaml`), far below the 76,386-token input a real HolyClaude interactive request measured during Task 6's verification, so it would overflow on realistic prompts anyway. In practice, on a Claude Pro outage the combo fails closed, not gracefully: the middle leg rejects on shape, the terminal leg overflows on context. The combo is kept for Omniroute-side attribution/logging and lane-scoping (it's what ties usage to the `holyclaude-interactive` key and keeps this traffic on the allowed-combo list), not because it provides real resilience — treat this as best-effort/fail-closed, not degradation. A `postStart` hook patches `~/.claude/settings.json` with these on every boot: three keys in its `env` block (`ANTHROPIC_BASE_URL`, `ANTHROPIC_MODEL`, `ANTHROPIC_AUTH_TOKEN`) plus the top-level `model` field — four values in total — because Claude Code reads `settings.json`'s env over real container env vars, so setting them as plain container env alone would not take effect. One consequence worth knowing: because the top-level `model` field is unconditionally overwritten every boot, any in-session `/model` choice a user makes is silently reverted back to `coding-deep` on the next pod restart. `persist-claude-json.mjs`'s OAuth-session persistence no longer applies to Claude Code's auth on this PVC. See "Known Omniroute limitations" below for two real, currently-unresolved gaps in how this lane-isolation policy is actually enforced), **TaskMaster AI** (`PERPLEXITY_API_KEY`, chosen specifically to avoid colliding with Claude Code's now-retired OAuth-based abstention from `ANTHROPIC_API_KEY`), and **OpenCode** (its own interactive auth, an explicit scoped exception — see below). Gemini CLI, OpenAI Codex, Cursor, Junie, and Pi Coding Agent are installed (unavoidable side effect of the `full` variant) but issued no credentials and no CloudCLI integration wiring. Single `openebs-hostpath` PVC (50Gi, retained), mounted narrowly at specific subPaths — `~/.claude`, `~/.cloudcli`, `~/.config/opencode`, `~/.taskmaster`, `~/.caveman`, `~/.hindsight`, `~/.claude-code-ui`, `/workspace`, plus several `~/.local/share`/`~/.local/state` XDG dirs (see `helmrelease.yaml`'s `persistence.home.globalMounts` for the current full list) — never the whole `/home/claude`. An earlier whole-`/home/claude` mount (matching this PVC's still-current subPath naming, so no data migration was needed when this was narrowed) shadowed everything the image bakes into that directory at build time, most critically `~/.local/bin` (the real `claude`/`cursor-agent`/`junie` binaries) — nothing in HolyClaude's entrypoint/bootstrap restores missing image content onto an empty PVC, so every fresh pod hit `claude: command not found`. This mirrors upstream's own docker-compose.yaml (`~/.claude`, `/workspace`) plus the two additions this deployment needs. The `gh-auth` init container runs before the app container's own `~/.config/gh` persistence symlink exists, so it points `GH_CONFIG_DIR` directly at `~/.claude/.config/gh` (inside the persisted `.claude` subtree) rather than relying on the (now unmounted) `~/.config/gh` default. Terminal access is **CloudCLI's built-in web terminal** (`node-pty` + xterm.js over WebSocket, port 3001) — not a code-server sidecar like openclaw's; `claude`/`task-master`/`opencode` are all on `$PATH` inside it. Runs as **root** with `SYS_ADMIN`+`SYS_PTRACE` capabilities and `seccompProfile: Unconfined` — required for the sandboxed Chromium/Playwright browser stack the image bundles, not optional hardening debt left undone; see the scoped-exception note below. The `ai` namespace is labeled `pod-security.kubernetes.io/{enforce,audit,warn}: privileged` (patched via `kubernetes/apps/ai/kustomization.yaml`, specifically to accommodate holyclaude's SYS_ADMIN/SYS_PTRACE + Unconfined-seccomp needs — see that file's own comment) — it is not an unlabeled, permissive-by-cluster-default namespace. Tightening this label to `baseline` or `restricted` later would break this pod without an explicit exemption for holyclaude. **Cluster RBAC added 2026-09-02**, mirroring openclaw's `cluster-admin` pattern exactly (`rbac.yaml`): a `holyclaude` ServiceAccount (`serviceAccount.holyclaude` in the HelmRelease values) bound to the built-in `cluster-admin` ClusterRole, with `automountServiceAccountToken: true` so every container in the pod gets a self-refreshing SA token at the standard path. Two consumers: a `kube-mcp` sidecar (`ghcr.io/containers/kubernetes-mcp-server:v0.0.66`, same image/config as openclaw's, `localhost:8081` in-pod only — registering it in Claude Code/OpenCode's own MCP config is a separate per-tool follow-up, not yet done) and a `00-render-kubeconfig` init container that writes a kubeconfig to `/workspace/home-ops/kubeconfig` referencing that same SA token/CA cert (`tokenFile`/`certificate-authority` pointing at the projected paths, no embedded credential) rather than copying the operator's real local `admin@kubernetes` kubeconfig into a Secret — so `kubectl`/`flux`/`task` work from a `/workspace/home-ops` checkout the same way they do locally, without a static admin credential ever leaving the operator's machine. Named to sort before `gh-auth`/`home-perms` so `home-perms`'s `chown -R 1000:1000 /workspace` still fixes ownership on the freshly written file. A second new mount, `persistence.sops-age`, projects the existing global `sops-age` Secret's `age.agekey` key (same key material Flux itself decrypts with, `kubernetes/components/common/sops-age.sops.yaml`) to `/workspace/home-ops/age.key`, giving that same checkout a working `SOPS_AGE_KEY_FILE` — no second copy of the key. Together these support running this repo's own `task`/`sops`/`kubectl`/`flux` tooling directly from inside HolyClaude's terminal, plus MCP-based cluster access for the agent. Git identity inside the container is `BarryBot`/`github+barrybot@beholdthehurricane.com`, a dedicated bot identity distinct from the user's own, so commits made from inside HolyClaude are visually distinguishable in history. A `gh-auth` init container runs `gh auth login --with-token` against `GITHUB_TOKEN` on every boot to persist gh credentials onto the PVC. `GITHUB_TOKEN`/`PERPLEXITY_API_KEY` are SOPS-encrypted, `CHANGEME`-gated the same way every other secret-bearing app in this repo handles first-deploy-before-real-credentials. **OTel export added for issue #707** (`prometheusrule.yaml`, `grafanadashboard.yaml`): the `app` container now sets `CLAUDE_CODE_ENABLE_TELEMETRY=1` and OTLP metrics/logs env vars pointed directly at `metrics.68cc.io`/`logs.68cc.io`'s native OTLP ingest paths (no in-cluster OTel Collector — both endpoints already accept OTLP directly), tagged `deployment.environment=holyclaude`. Unlike the `ANTHROPIC_*`/`OMNIROUTE_ANTHROPIC_*` values above, this needed no `postStart` `settings.json` patch (`OTEL_*` is read from plain process env). **Confirmed end-to-end 2026-09-23** via a one-shot `claude -p` run inside the pod: `claude_code.session.count`/`cost.usage`/`token.usage`/`active_time.total` landed in VictoriaMetrics and `claude_code.user_prompt` landed in VictoriaLogs within one export interval. Notably, VictoriaMetrics does **not** sanitize OTel names into Prometheus convention — the real series/label names are dotted verbatim (`claude_code.session.count`, `deployment.environment`), not underscored with a `_total` suffix as first assumed; PromQL against them needs MetricsQL's quoted-name selector (`{"claude_code.session.count", "deployment.environment"="holyclaude"}`). See `docs/runbooks/agent-telemetry.md` for the laptop/Codex-side config this repo can't apply directly, the full quoted-selector writeup, and what was explicitly deferred (Hindsight queue-depth, hook-failure alerts).
