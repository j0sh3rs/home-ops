## Hindsight deployment notes (2026-09-24/25, #701/#702)

- **hindsight** (`kubernetes/apps/ai/hindsight/`) — [vectorize-io/hindsight](https://github.com/vectorize-io/hindsight) memory server, OCI chart `oci://ghcr.io/vectorize-io/charts/hindsight` 0.10.1, image 0.10.1 (`values.version`). API (queue worker in-process, `worker.enabled: false`) + control plane, 1 replica each. **Sole memory layer** since 2026-09-25 (OpenViking retired — see its note above); the #704 recall eval is still open; Codex/Pi plugins and backfill (#703) still pending. Design: `docs/superpowers/specs/2026-09-24-hindsight-deployment-design.md`; plan: `docs/superpowers/plans/2026-09-24-hindsight-deployment.md`. **Routes**: `hindsight.68cc.io` → API `:8888` (per-client bearer keys via the `StaticKeysTenantExtension` below, no forwardAuth) and `hindsight-ui.68cc.io` → control plane `:3000` (Authentik forwardAuth) — both `traefik-internal` (LAN-only); in-cluster, `hindsight-api.ai.svc.cluster.local:8888`. `traefik-internal`'s `writeTimeout` was raised 120s → 150s for Hindsight's synchronous large calls (commit `8217890e`). **DB**: CNPG `postgres17`, database `hindsight` owned by managed role `hindsight`, pgvector via a CNPG `Database` resource (`database-hindsight.yaml`, `extensions: [vector]`) because Hindsight's own migrations check for pgvector but never create it — a plain `postgres-init` initContainer can't create extensions either. Role secret `hindsight-db-creds` (ns `databases`) must match `postgres-password` in `hindsight-secret` (ns `ai`) — rotate both together. **Auth**: upstream `StaticKeysTenantExtension` shipped as a ConfigMap (`configmap-extension.yaml`, verbatim from v0.10.1 — regenerate on chart bump) on `PYTHONPATH=/app/extensions`. `HINDSIGHT_API_TENANT_USERS` maps laptop-claude, holyclaude, and control-plane keys, in that order, all to user `josh` → one shared schema `user_josh` (shared memory, per-client revocable keys). API routes are `/v1/default/...` regardless of tenant.
  - **LLM**: retain/reflect/consolidation route through Omniroute (`http://omniroute.ai.svc.cluster.local:20128/v1`) as `llamaswap/reasoner` = `gpt-oss-20b`, via a dedicated `hindsight-retain` Omniroute key (id `00bd2041-1b17-4817-aabb-39695aa002e0`): `modelAccessMode: "restricted"`, `allowedModels: ["llamaswap/reasoner"]`, `compressionEnabled: false` — cannot reach the Claude lane (see the Anthropic lane isolation policy above). gpt-oss-20b is the dGPU's sole always-on chat model, 5 parallel slots × 32768 tokens each (raised 4→5, commit `7481daaa`), alongside Hindsight's own concurrency caps: global `HINDSIGHT_API_LLM_MAX_CONCURRENT=5`, retain 2, consolidation 1, mental-model refresh 1 — the per-op caps nest inside the global cap, so one slot always stays free for reflect, but only within Hindsight's own traffic: atuin (`coder-large`/`frontier`) and argus (`coder-large`) address this same `gpt-oss-20b` model and share the same 5 physical slots, uncounted by these caps. `HINDSIGHT_API_RETAIN_MAX_COMPLETION_TOKENS=16000` (upstream's default 64000 can't fit a 32k slot), `HINDSIGHT_API_RETAIN_LLM_REASONING_EFFORT=low`, `HINDSIGHT_API_LLM_STRICT_SCHEMA_RETAIN=true` (strict `json_schema` response_format, added 2026-09-25 — see the incident below).
  - **Memory Defense (#702)**: on for every bank via `HINDSIGHT_API_DEFAULT_BANK_TEMPLATE` (`memory_defense: {enabled: true, rules: [{on: sensitive_data, action: redact}]}` + `retain_extraction_mode: concise`). Verified with planted fake secrets on both the synchronous and the async (worker) retain paths: 0 raw values landed in memories, chunks, or document `original_text`; `REDACTED:github_token` / `REDACTED:db_url_postgres` markers present instead. The recurring `Failed to load bank config ... relation "public.banks" does not exist` log line is the per-sub-batch bank-config read on the write path (upstream `config_resolver.py` returns `{}` on error, so the failed lookup is swallowed silently) — Memory Defense redaction itself was verified on the async path as above, but other per-bank overrides (e.g. `retain_extraction_mode`) are unverified on that same path given this lookup failure. Worth an upstream issue.
  - **Worker durability**: `HINDSIGHT_API_WORKER_ID=hindsight-api` (stable; default is the pod hostname) plus a true `type: Recreate` strategy applied via `postRenderers` (the chart has no strategy value) — the old pod is fully gone before the new one is created. A RollingUpdate maxSurge 0 / maxUnavailable 1 strategy was tried first and rejected: it does not serialize old-then-new for a single replica, since Kubernetes creates the new pod as soon as the old pod gets a deletionTimestamp, not after it actually exits, so the two pods could run concurrently for up to the 30s termination grace period. Recreate itself needed a one-time, out-of-band live patch (`kubectl patch deploy -n ai hindsight-api --type=json -p '[{"op":"replace","path":"/spec/strategy","value":{"type":"Recreate"}}]'`) to clear the live Deployment's SSA-owned `rollingUpdate` fields, which otherwise survive the postRenderer patch and make the API refuse `rollingUpdate` + `Recreate` together — see `helmrelease.yaml`'s postRenderer comment for the full history. Reason a stop-then-start rollout matters at all: startup recovery only reclaims `processing` rows owned by the worker's own id, and retains are serialized per document / consolidation per bank, so a single orphaned row wedges the whole queue. **No alert exists yet on a wedged queue** — see the 2026-09-24/25 backlog incident below and the deferred-alert entry in `docs/runbooks/agent-telemetry.md`.
  - **Clients**: plugin `@vectorize-io/hindsight-coding-agents@0.7.0`, `autoUpdate: false`, `retainExtractionMode: "concise"`, **`autoInject: "recall"`** (operator decision 2026-09-25, superseding the spec's `reflect` — the plugin's 20s first-prompt reflect timed out on every session even against a healthy backend, adding ~40s; recall is LLM-free, agents can still call `hindsight_reflect` on demand). Installed on this machine (`~/.hindsight/coding-agent.json`, external route) and on HolyClaude (`~/.hindsight` PVC subPath mount; `HINDSIGHT_API_URL=http://hindsight-api.ai.svc.cluster.local:8888` plain env + `HINDSIGHT_API_TOKEN` from `holyclaude-secret`). Shared bank `coding-agent::home-ops`. The plugin's hooks live in `~/.claude/settings.json`. **Not GitOps-managed**: the client plugin config itself (`~/.hindsight/coding-agent.json` — `autoInject: recall`, `autoUpdate: false`, `retainSessions`) lives on this machine's local disk and on HolyClaude's PVC, not in this repo. This machine's `autoUpdate` was once found flipped back to `true`; check both copies after any plugin maintenance.
  - **Known quirks (brief)**: HolyClaude's `postStart` leaves `~/.claude/settings.json` root:root after every restart, so a future in-pod plugin reinstall/upgrade needs a chown first; `/metrics` and `/docs` on `hindsight.68cc.io` are unauthenticated (LAN-only, upstream registers them outside auth); the API pod's 4Gi limit is above the repo's <2Gi guideline (in-process torch models for bge-small-en-v1.5 + ms-marco-MiniLM-L-6-v2, accepted in the spec — right-size after the retain trial).
  - **2026-09-24/25 backlog incident** — the operator-accepted negative test standing in for the plan's Task 9 (skipped):
    1. **Omniroute 15s execution cap.** Omniroute's limiter reuses `resilienceSettings.requestQueue.maxWaitMs` (global 15000) as the execution deadline for the whole upstream call (`open-sse/services/rateLimitManager.ts`), not just a queue-wait timeout. The `llama-swap` connection (`384d2f37-ef5f-4266-ae72-d027c309a815`) had no override (`llama-swap-apu` already had 120000), so every gpt-oss call over 15s got a pre-output 504, and repeated failures tripped 429 model lockouts (510 504s in 16h). Fixed 2026-09-25 by PATCHing `rateLimitOverrides: {"maxWaitMs": 120000}` (schema maximum) on that connection **plus an Omniroute restart** — overrides load once per process, so the PATCH's in-process refresh never reaches the chat path. This override lives only in Omniroute's DB, not in git — re-apply it if Omniroute's data is ever reset. Cross-referenced in "Known Omniroute limitations" below.
    2. **Orphaned claims.** Hostname-based worker ids left 6 retains stuck `processing` under a replaced pod for 16h, blocking 10 pending retains behind them. Cleared by hand with Hindsight's own reclaim UPDATE; prevented going forward by the stable worker id above.
    3. **Schema drift.** Soft schema mode let gpt-oss drop required fact fields (~40% of retains "unusable after 4 attempts"); fixed with strict schema (llama-server grammar), pre-verified through Omniroute before enabling.
    Outcome: queue drained from 41 pending / 10 processing to 2/2 in ~30 min with 0 failures in the following 15 min; consolidation and graph maintenance running normally afterward.
