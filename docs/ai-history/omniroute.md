History moved verbatim from `kubernetes/apps/ai/CLAUDE.md` on 2026-09-25 (#710); current state lives in that file.

## Original namespace overview (gateway topology, Anthropic lane policy) — as of 2026-09-25

Fully self-hosted AI stack — no third-party/cloud LLM providers for automated workloads; the one narrow, gated exception is interactive human use via HolyClaude (see the Anthropic lane policy below and the scoped exception in "Decisions explicitly rejected"). Topology: **omniroute** (`kubernetes/apps/ai/omniroute/`) is the AI-namespace gateway, fronting both **llama-swap** instances (`http://llama-swap.ai.svc.cluster.local:8080/v1`, `http://llama-swap-apu.ai.svc.cluster.local:8080/v1`) plus a **cliproxyapi** sidecar (in-pod only, `127.0.0.1:8317`) that reuses Claude Code's and Codex/ChatGPT CLI's own OAuth sessions as OpenAI-compatible (`cliproxyapi/gpt-*`) and, for Claude, also Anthropic-native `/v1/messages`-compatible (`cliproxyapi/claude-*`) backends. **argus** (observability/triage, bundles HolmesGPT) and **atuin-ai-server** route through Omniroute (`http://omniroute.ai.svc.cluster.local:20128/v1`), each with its own dedicated Omniroute inference key (`sk-...`), addressing models either by a named routing **combo** (multi-leg with fallback, e.g. `coding-fast`, `coding-deep`, `debugging`) or a bare `<provider>/<model>` reference (`llamaswap/coder-large`, `llamaswapapu/vlm`). The shared memory layer is **hindsight** (see its bullet below); **openviking** was retired 2026-09-25 along with the omniroute shim sidecar and the OpenViking-only embed/vlm/rerank models. See the LiteLLM/OmniRoute history note directly below, and `docs/superpowers/specs/2026-09-07-omniroute-revival-design.md`, `2026-09-08-omniroute-phase2-switchover-design.md`, and `2026-09-16-omniroute-anthropic-lane-design.md` for the full LiteLLM-removal → Omniroute-revival → Phase 2 switchover → Anthropic-lane design history. **Anthropic (Claude) lane isolation policy**: `cliproxyapi/claude-*` models, whether bare or via a combo, are reserved for interactive use only — HolyClaude is the sole interactive consumer (see its bullet below); every automated consumer is expected to use the OpenAI/Codex lane or a local model instead. See "Known Omniroute limitations" below for two real gaps in how that policy is actually enforced today. The external debug route (`omniroute.68cc.io`) is gated by Authentik forwardAuth. Local inference only otherwise: llama-swap (GGUFs on AMD GPU), faster-whisper (STT), piper (TTS) via Home Assistant.

## Known Omniroute limitations (accepted risk, not fixed by this project)

Both findings below were confirmed live during `.superpowers/sdd/2026-09-16-omniroute-anthropic-lane/` (Tasks 1 and 4) and explicitly risk-accepted by the operator on 2026-09-17 — read them alongside the Anthropic lane isolation policy at the top of this file, which they both partially undermine in practice.

- **`/v1/messages` has no authentication at all.** Confirmed live against this Omniroute build/version: a garbage Bearer token AND no `Authorization` header at all both returned `200` with genuine Claude inference. Reproduced independently twice while investigating a leaked key — hard-deleting the key's ID via `DELETE /api/keys/<id>` and a full `omniroute` pod restart (fresh process, new pod name) neither one closed the gap, ruling out a caching explanation: the endpoint simply does not check the credential. This means any pod that can reach `omniroute.ai.svc.cluster.local:20128` can currently get free, unrestricted Claude inference regardless of any key-based control — including bypassing the "interactive only" Anthropic lane policy above. **Explicitly accepted as a known risk by the operator (2026-09-17)**: single-user home-lab, no untrusted in-cluster workloads today. Not fixed by this project — revisit if Omniroute is upgraded and this is resolved upstream, or if the cluster's trust model changes (e.g. running less-trusted workloads). Full investigation: the "Outcomes / findings" section of `docs/superpowers/specs/2026-09-16-omniroute-anthropic-lane-design.md`.
- **Per-key `blockedModels` is unreachable via the management API.** `PATCH /api/keys/[id]`'s validation schema (`updateKeyPermissionsSchema`, in the running container's own `/app/src/shared/validation/schemas/keys.ts`) never declares `blockedModels` as a field, despite the DB column, the enforcement logic, and the dashboard UI all supporting it — confirmed via source read, not just observed behavior. Any `blockedModels` value sent in a PATCH is silently stripped by Zod's default unknown-key handling before the route ever sees it: a request containing *only* `blockedModels` 400s ("No valid fields to update"), while padding it with a real field like `noLog` returns a misleading `200` that still drops `blockedModels` (confirmed via a GET-after-PATCH round trip). All 6 remaining automated Omniroute keys (`phase1-local-inference`, `openclaw`, `argus-holmes`, `atuin-ai-server`, `controller-compression-probe`, `home-assistant-conversation`) currently have `modelAccessMode: "all"` with empty `allowedModels`/`blockedModels` — no per-key restriction of any kind (`openviking-embedding`/`openviking-vlm` were revoked 2026-09-25 with OpenViking). This means the only real enforcement of "automated consumers can't reach Claude" **via Omniroute** is that no remaining automated combo references Claude — the `openviking-vlm` combo, which once carried the Claude leg this fix removed, was deleted outright 2026-09-18 when openviking's vlm leg bypassed Omniroute entirely, rather than kept around with just the leg removed — not backed by a second, independent key-level deny-list the way the original design intended. **`hindsight-retain` (added 2026-09-24, #701) is the one exception to the "no per-key restriction" state above**: it was created `modelAccessMode: "restricted"` with `allowedModels: ["llamaswap/reasoner"]` from the start, rather than retrofitted — see the hindsight bullet above. **Explicitly accepted (2026-09-17)**: the combo-level fix is considered sufficient for now; converting all 8 (now effectively 7, since hindsight-retain already ships restricted) automated keys to `modelAccessMode: "restricted"` + an `allowedModels` allow-list was considered and explicitly declined as a bigger, riskier change than this finding's scope. Revisit if Omniroute ever adds real support for `blockedModels` on this endpoint, or if a future combo/config change risks reintroducing a Claude reference into an automated path. Full investigation: the "Outcomes / findings" section of `docs/superpowers/specs/2026-09-16-omniroute-anthropic-lane-design.md`.
- **Per-connection `maxWaitMs` is an execution deadline, not a queue-wait timeout.** Omniroute's limiter reuses `resilienceSettings.requestQueue.maxWaitMs` on each provider connection as the deadline for the entire upstream call, not just time spent waiting in queue before dispatch (`open-sse/services/rateLimitManager.ts`) — confirmed live 2026-09-25 when the `llama-swap` connection's unset override (schema default, effectively the global 15000ms) truncated every gpt-oss-20b call over 15s with a pre-output 504, see the hindsight bullet's 2026-09-24/25 backlog incident above for the full timeline. 120000ms is the schema maximum. Any override is **live-DB-only** (not tracked in git) and requires an Omniroute pod restart to take effect — a PATCH's in-process refresh does not reach the chat path. Check this on every new connection a consumer is added behind, not just its Omniroute key's model access.
- **~~The shim's direct-to-CLIProxyAPI path has no model allow-list~~ — resolved 2026-09-25, path removed.** The omniroute `shim` sidecar (OpenViking's `vlm` leg, 2026-09-18) forwarded `model` verbatim to CLIProxyAPI with no allow-list; it was removed along with OpenViking, so this risk no longer exists. History: git log and `docs/superpowers/specs/2026-09-18-openviking-vlm-direct-shim-design.md`.
