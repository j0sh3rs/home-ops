# AI namespace

Fully self-hosted AI stack — no third-party/cloud LLM providers for automated workloads; the one narrow, gated exception is interactive human use via HolyClaude (see the Anthropic lane policy below and the scoped exception in "Decisions explicitly rejected"). Topology: **omniroute** (`kubernetes/apps/ai/omniroute/`) is the AI-namespace gateway, fronting both **llama-swap** instances (`http://llama-swap.ai.svc.cluster.local:8080/v1`, `http://llama-swap-apu.ai.svc.cluster.local:8080/v1`) plus a **cliproxyapi** sidecar (in-pod only, `127.0.0.1:8317`) that reuses Claude Code's and Codex/ChatGPT CLI's own OAuth sessions as OpenAI-compatible (`cliproxyapi/gpt-*`) and, for Claude, also Anthropic-native `/v1/messages`-compatible (`cliproxyapi/claude-*`) backends. **openclaw** (sole code-automation agent, real-time memory via the `openviking` plugin — see below) talks **directly** to llama-swap's OpenAI-compatible endpoint and needs no key; **argus** (observability/triage, bundles HolmesGPT), **openviking** (context/memory server, embedding + vlm), and **atuin-ai-server** all route through Omniroute (`http://omniroute.ai.svc.cluster.local:20128/v1`) instead, each with its own dedicated Omniroute inference key (`sk-...`), addressing models either by a named routing **combo** (multi-leg with fallback, e.g. `coding-fast`, `coding-deep`, `debugging`) or a bare `<provider>/<model>` reference (`llamaswap/coder-large`, `llamaswapapu/vlm`). See the LiteLLM/OmniRoute history note directly below, and `docs/superpowers/specs/2026-09-07-omniroute-revival-design.md`, `2026-09-08-omniroute-phase2-switchover-design.md`, and `2026-09-16-omniroute-anthropic-lane-design.md` for the full LiteLLM-removal → Omniroute-revival → Phase 2 switchover → Anthropic-lane design history. **Anthropic (Claude) lane isolation policy**: `cliproxyapi/claude-*` models, whether bare or via a combo, are reserved for interactive use only — HolyClaude is the sole interactive consumer (see its bullet below); every automated consumer is expected to use the OpenAI/Codex lane or a local model instead. See "Known Omniroute limitations" below for two real gaps in how that policy is actually enforced today. The external debug route (`omniroute.68cc.io`) is gated by Authentik forwardAuth. Local inference only otherwise: llama-swap (GGUFs on AMD GPU), faster-whisper (STT), piper (TTS) via Home Assistant.

**n8n, OpenCode, agent-canvas, cognee, and the kelos-system namespace** (Kelos + its GitHub-issue-spawner agents) **were removed 2026-08-14** — collapsing multiple overlapping code-agent surfaces down to openclaw alone (OpenCode later returned as a scoped, interactive-only exception inside holyclaude — see "Decisions explicitly rejected" below). **LiteLLM and OmniRoute were also removed that same day, but the removal did not stick.** OmniRoute was revived 2026-09-07 using a materially different mechanism than the one originally rejected (`docs/superpowers/specs/2026-09-07-omniroute-revival-design.md` — CLIProxyAPI CLI-session reuse, not the earlier Playwright/Chromium browser-scraping approach), then switched over 2026-09-08 to be the live AI-namespace gateway fronting both llama-swap instances plus the cliproxyapi sidecar (`docs/superpowers/specs/2026-09-08-omniroute-phase2-switchover-design.md`). **LiteLLM and litellm-operator were fully removed as part of that same Phase 2 switchover** (not kept as cold standby, per `kubernetes/apps/ai/kustomization.yaml`'s own header comment) — every consumer that previously routed through LiteLLM (openviking, argus, atuin-ai-server) now routes through Omniroute instead, and there is no `kubernetes/apps/ai/litellm/` directory left in this repo. See the "Decisions explicitly rejected" section's OmniRoute and gateway-in-front-of-llama-swap entries for how those two now-reversed rejections are annotated.

**memini (memory/embedding backend, `memini.68cc.io`) was archived 2026-08-16** — its own plugin extension threw a command-registration error on every openclaw boot ("Command name must start with a letter..."), and the wiki-vault rendering built on top of it (`memory-wiki` plugin) went with it. `memory-core` stays explicitly disabled rather than silently becoming the default backend; the `openviking` plugin (`@openviking/openclaw-plugin` from ClawHub) claims `plugins.slots.memory` instead, live since shortly after memini's removal — see `archive/memini/` and the openclaw bullet below.

LangFuse (observability), AnythingLLM (RAG), Open WebUI (chat UI), and Goose (code automation agent) were removed 2026-07-01 — unused, no consumers beyond a chat UI nobody used; see `docs/runbooks/anythingllm-role-and-overlap.md` and `archive/{langfuse,anythingllm,open-webui,goose}/` if reuse is considered later. claude-code (headless code-automation engine, daemon + runner Job template) was also removed 2026-07-01.

**ollama was archived 2026-08-16** — deployed as a same-node comparison spike against llama-swap (both need bigboi-jms-01's single GPU, so they ran mutually exclusive via manual HelmRelease suspend/resume); spike concluded, llama-swap remains the sole chat/completion engine. See `archive/ollama/`.

The combo is kept for Omniroute-side attribution/logging and lane-scoping (it's what ties usage to the `holyclaude-interactive` key and keeps this traffic on the allowed-combo list), not because it provides real resilience — treat this as best-effort/fail-closed, not degradation. ## Known Omniroute limitations (accepted risk, not fixed by this project)

Both findings below were confirmed live during `.superpowers/sdd/2026-09-16-omniroute-anthropic-lane/` (Tasks 1 and 4) and explicitly risk-accepted by the operator on 2026-09-17 — read them alongside the Anthropic lane isolation policy at the top of this file, which they both partially undermine in practice.

- **`/v1/messages` has no authentication at all.** Confirmed live against this Omniroute build/version: a garbage Bearer token AND no `Authorization` header at all both returned `200` with genuine Claude inference. Reproduced independently twice while investigating a leaked key — hard-deleting the key's ID via `DELETE /api/keys/<id>` and a full `omniroute` pod restart (fresh process, new pod name) neither one closed the gap, ruling out a caching explanation: the endpoint simply does not check the credential. This means any pod that can reach `omniroute.ai.svc.cluster.local:20128` can currently get free, unrestricted Claude inference regardless of any key-based control — including bypassing the "interactive only" Anthropic lane policy above. **Explicitly accepted as a known risk by the operator (2026-09-17)**: single-user home-lab, no untrusted in-cluster workloads today. Not fixed by this project — revisit if Omniroute is upgraded and this is resolved upstream, or if the cluster's trust model changes (e.g. running less-trusted workloads). Full investigation: the "Outcomes / findings" section of `docs/superpowers/specs/2026-09-16-omniroute-anthropic-lane-design.md`.
- **Per-key `blockedModels` is unreachable via the management API.** `PATCH /api/keys/[id]`'s validation schema (`updateKeyPermissionsSchema`, in the running container's own `/app/src/shared/validation/schemas/keys.ts`) never declares `blockedModels` as a field, despite the DB column, the enforcement logic, and the dashboard UI all supporting it — confirmed via source read, not just observed behavior. Any `blockedModels` value sent in a PATCH is silently stripped by Zod's default unknown-key handling before the route ever sees it: a request containing *only* `blockedModels` 400s ("No valid fields to update"), while padding it with a real field like `noLog` returns a misleading `200` that still drops `blockedModels` (confirmed via a GET-after-PATCH round trip). All 8 automated Omniroute keys (`phase1-local-inference`, `openviking-embedding`, `openviking-vlm`, `openclaw`, `argus-holmes`, `atuin-ai-server`, `controller-compression-probe`, `home-assistant-conversation`) currently have `modelAccessMode: "all"` with empty `allowedModels`/`blockedModels` — no per-key restriction of any kind. This means the only real enforcement of "automated consumers can't reach Claude" is the combo-level fix above (`openviking-vlm`'s Claude leg removed, and no other automated combo references Claude either) — not backed by a second, independent key-level deny-list the way the original design intended. **Explicitly accepted (2026-09-17)**: the combo-level fix is considered sufficient for now; converting all 8 automated keys to `modelAccessMode: "restricted"` + an `allowedModels` allow-list was considered and explicitly declined as a bigger, riskier change than this finding's scope. Revisit if Omniroute ever adds real support for `blockedModels` on this endpoint, or if a future combo/config change risks reintroducing a Claude reference into an automated path. Full investigation: the "Outcomes / findings" section of `docs/superpowers/specs/2026-09-16-omniroute-anthropic-lane-design.md`.

## Decisions explicitly rejected (do not relitigate without new evidence)

- **Continue.dev** — explicitly rejected 2026-08-17. Was the sole planned consumer of `coder-fim` (FIM autocomplete on `llama-swap-apu`); that model block, its litellm mirror, and its init-container fetch were all removed. Do not reintroduce Continue.dev or re-add a FIM-only model without a new, explicit ask.
- **AMD GPU Operator, cluster-wide / driver-managed mode** — wrong fit for the bee-* APU nodes: KMM-managed DKMS conflicts with in-box `amdgpu` extension; APUs not on Instinct HCL; ANR/NPD/DCM features all require Instinct silicon. This rejection still stands for bee-*. See [memory: project-amd-gpu-stack].
  **Scoped exception, adopted for `bigboi-jms-01` (dgpu tier) AND `bee-jms-03` (apu-light tier) via two disjoint driverless `DeviceConfig`s, each scoped to exactly one node by a unique `node.kubernetes.io/gpu-tier` label value**: `kubernetes/apps/kube-system/amd-gpu/` now runs the ROCm GPU Operator (`gpu-operator-charts`) with `DeviceConfig.spec.driver.enable: false` on both `DeviceConfig`s — one selects `{node.kubernetes.io/gpu-tier: dgpu}` (bigboi-jms-01), the other `{node.kubernetes.io/gpu-tier: apu-light}` (bee-jms-03). Driverless mode means KMM is never asked to build/DKMS-install anything — Talos's `siderolabs/amdgpu` extension still owns the kernel module on every node — and the per-node-unique label values mean KMM/NFD never evaluate any node outside the one each selector targets. Both objections above (DKMS conflict, Instinct-only features) are sidestepped by construction, not overridden. `bee-jms-01`/`bee-jms-02` remain excluded on hardware grounds (3 GiB dedicated VRAM vs `bee-jms-03`'s 16 GiB BIOS-expanded VRAM) — do not widen either selector to include them.
- **ROCm DKMS** — Talos rootfs immutable; no path. ROCm userspace only matters inside workload containers, not at kernel level.
- **Replacing llama-swap with Ollama** — duplicates the same role; would lose curated GGUF + model-fetch control. One engine policy.
- **Keeping a gateway (LiteLLM or otherwise) in front of llama-swap** — **decision reversed, no longer standing.** Originally rejected/removed 2026-08-14: once cloud-provider fan-out was off the table and this was a single-user home-lab, a gateway's remaining value (per-consumer virtual keys, cost tracking, response caching) was already mostly inert for LiteLLM specifically — `disable_spend_logs: true`, Prometheus metrics disabled (needs LiteLLM Enterprise license, 404s), and llama-swap already exposed the same model-alias abstraction natively. That original LiteLLM-specific reasoning still stands (LiteLLM was never worth reinstating). But the underlying "no gateway at all" conclusion was reversed by the OmniRoute revival (2026-09-07) and Phase 2 switchover (2026-09-08): Omniroute is now the live gateway in front of both llama-swap instances, adopted for a capability llama-swap alone can never provide — the `cliproxyapi` sidecar's Claude/Codex CLI-session reuse (see the top-of-file overview and the holyclaude bullet above) — not because LiteLLM's original inert-features rationale became more compelling.
- **OmniRoute — REVIVED, no longer a rejected decision.** Originally rejected/removed 2026-08-14 over ToS-boundary concerns (its CLI-session-reuse mode's Playwright/Chromium scraping of Claude-web/Gemini-web — uTLS spoofing, multi-account rotation, device-profile learning) and cloud-dependency/attack-surface concerns. **Revived 2026-09-07 using a materially different mechanism**, explicitly not the browser-scraping approach: CLIProxyAPI's CLI-session reuse, which authenticates the same way the CLI tools (Claude Code, Codex) already do (their own first-party OAuth device-flow login), rather than scraping a web UI. Omniroute is now the live AI-namespace gateway, fronting both llama-swap instances plus the cliproxyapi sidecar. See the top-of-file overview and `docs/superpowers/specs/2026-09-07-omniroute-revival-design.md` (revival), `2026-09-08-omniroute-phase2-switchover-design.md` (Phase 2 switchover, full LiteLLM removal), and `2026-09-16-omniroute-anthropic-lane-design.md` (Anthropic/Claude lane isolation policy) for the full history and rationale. Do not treat this file's own historical "removed 2026-08-14" framing (still visible above, preserved for the record) as still accurate.
